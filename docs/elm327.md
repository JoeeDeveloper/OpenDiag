# ELM327-style adapters

```bash
opendiag scan --elm327 COM4                      # UDS over CAN, tester 0x7E0, module 0x7E8
opendiag dtc read --elm327 /dev/ttyUSB0 --elm-baud 115200 --tester-id 0x7E1 --ecu-id 0x7E9
opendiag scan --simulate-elm327                  # software adapter + virtual ECU, no hardware
```

The adapter is switched to raw CAN mode (`ATCAF0`, 11-bit, 500 kbit/s); ISO-TP and UDS run in OpenDiag's own
stack, so everything that works over UDS (scan, fault codes, the guarded clear flow) works the same way here.

## What you give up

- **Only UDS on 11-bit CAN.** No K-line (KW1281, KWP2000), no 5-baud or fast init, no TP2.0, no 29-bit ids. Use a
  K-line cable or SocketCAN for those.
- **Slow and fragile.** The adapter answers each frame we send at its own pace; long multi-frame replies can
  overflow its small buffer (`BUFFER FULL`, reported as an error).
- **Clones differ.** Many cheap adapters implement only part of the AT command set. If one refuses a command,
  `init` says which one. Baud rates vary (38400 default, some 115200 or 9600).
- Only commands built inside OpenDiag are sent; there is no way to pass raw AT text through.

## Status

Never run against a real adapter. The tests use a software emulator written from the same understanding of the
data sheet as the driver, so they prove the code is self-consistent, not that it matches real hardware. See
[status.md](status.md) and the first-hardware checklist there.

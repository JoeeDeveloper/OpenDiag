# KW1281

The block protocol of older VAG controllers (roughly 1990s to mid-2000s). Code: `crates/opendiag-proto/src/kw1281/`
(codec, client, byte-level virtual module). Sources: KW1281Test (MIT) and the pages it cites; see
[../sources.md](../sources.md). **Nothing here has run against a real module.**

## Starting a session: 5-baud slow init

The tester sends the module address at **5 baud**, bit-banged: 1 start bit (low), 7 data bits least-significant first,
1 **odd** parity bit, 1 stop bit (high), 200 ms per bit (the serial driver toggles the line with a break signal and
flushes the junk that appears on RX afterwards). The module then answers at the port's normal baud (typically 10400,
sometimes 9600) with:

1. `0x55` (sync, so the tester can measure the baud rate),
2. keyword byte 1, keyword byte 2. For KW1281 the second is `0x8A`; anything else is refused with a hint that the module
   probably speaks [KWP2000](kwp2000.md) after slow init.

The tester replies with the **complement** of the second keyword (`0x75`). The module then sends its identification
blocks straight away (no inverted-address byte).

## Blocks

```
len  counter  title  data...  0x03
```

- `len` counts everything after itself, including the end byte `0x03`, so an ACK block is `03 cc 09 03`.
- `counter` runs through both directions: each block is the previous one plus 1 (wrapping at 256). The first block of
  a session can start anywhere; every later one is checked.
- The block-end byte `0x03` is the only byte that is **not** acknowledged. Every other byte is acknowledged by the
  receiver sending its bitwise complement, one byte at a time, in lock step. Cables echo what we send, so each byte
  we transmit also comes back (the client expects this unless told `--no-echo`).

Titles used (from the public documentation):

| Title | Meaning | | Title | Meaning |
|---|---|---|---|---|
| `0x00` | ReadIdent | | `0x29` | GroupRead |
| `0x05` | FaultCodesDelete (**gated**) | | `0xE7` | GroupRead response |
| `0x06` | End of session | | `0x21` / `0x22` / `0x2A` | Adaptation read / test / save |
| `0x07` | FaultCodesRead | | `0xE6` | Adaptation response |
| `0x09` / `0x0A` | ACK / NAK | | `0xF6` | ASCII data (identification) |
| `0xFC` | FaultCodes response | | | |

## The conversation

The module sends blocks; the tester acknowledges each with an ACK block until the module sends an ACK block of its own,
which means "nothing more, your turn". To ask for something the tester sends a request block instead of an ACK, then
receives the reply blocks the same way. `keep_alive` is an ACK exchange; the module drops an idle session after a few
seconds.

- **Identification:** `0xF6` text blocks. If the first data byte of a block has its top bit set, more is available via
  ReadIdent (`0x00`).
- **Fault codes:** 3-byte records (code high, code low, status). `FF FF 88` means "no fault" and is skipped. Codes are
  shown as 5-digit decimals; the status byte is shown raw because its meaning is module-specific.
- **Measuring groups:** `0x29 <group>` returns `(formula, a, b)` triples, shown raw. Turning them into units needs a
  per-formula table that belongs in the open data format (see [../data-format.md](../data-format.md)).
- **Adaptation:** read (`0x21 ch`), test (`0x22 ch hi lo`) and save (`0x2A ch hi lo` plus a 24-bit workshop code), all
  answered with `0xE6 ch hi lo`. Test and save are **gated** and only reachable through the guarded flow
  ([../safety.md](../safety.md)). The reply to a *save* is unconfirmed, so any non-NAK answer is accepted and success is
  decided by reading the value back. The `Login` block is deliberately not implemented.

## Staying in sync (no checksum!)

Blocks carry no checksum; the per-byte complement is the only integrity check, so a corrupted or extra byte can leave
the two sides misaligned, and bytes we then acknowledge could be read by a module as the start of a command. So:

- A **block length under 3** or a **counter that is not the expected one** is *not acknowledged* (silence, not a
  plausible-looking ack).
- After the **first error** mid-session, nothing more is sent into it (even the end-of-session block); reconnect.
- A NAK from the module is a legitimate reply and does *not* break the session.

How a real module reacts to a desynchronised stream is unknown. The virtual module assumes it abandons the exchange.

## Timing

`ack_delay` 2 ms (pause before sending a complement), `block_gap` 25 ms (pause before sending a block), byte timeout
1000 ms, init timeout 3000 ms. These are **conservative placeholders**, not measured. A known real-world quirk (a
repeated sync byte during a session) is not handled.

# TP2.0 (VW Transport Protocol 2.0)

The CAN transport older CAN-era VAG modules use to carry [KWP2000](kwp2000.md). Code:
`crates/opendiag-proto/src/tp20/`. Source: a community write-up (`jazdw.net/tp20`) that its author says is
**reverse-engineered from captures, not from official documents**; see [../sources.md](../sources.md). Everything
here is unverified against a real module.

## Opening a channel

1. **Setup request** on CAN id `0x200`: `dest C0 rxLo rxV txLo txV app`. We ask the module to *transmit* on `0x300`
   (the request marks the receive id invalid). The 11-bit id is split as a low byte plus a high nibble; the nibble of
   the following byte is the validity (0 valid, 1 invalid) and the id's top 3 bits. Example:
   `01 C0 00 10 00 03 01`.
2. **Setup reply** on `0x200 + dest`: opcode `0xD0` is positive, `0xD6..0xD8` refuse. The ids in the reply are from
   the tester's side: the first is where we listen (`0x300`), the second where we must transmit (`0x740`).
3. **Parameters**: we send `A0 BS T1 T2 T3 T4` on the negotiated id; the module answers `A1 ...` with its own.
   Example: `A0 0F 8A FF 32 FF` then `A1 0F 8A FF 4A FF`.

A timing byte is `unit<<6 | scale`: unit 0 = 0.1 ms, 1 = 1 ms, 2 = 10 ms, 3 = 100 ms; `0xFF` means unused. So `0x8A`
is 100 ms, `0x4A` is 10 ms, `0x32` is 5 ms. `T1` is the time to wait for an ACK; `T3` the gap between packets.

Other control messages: `A3` channel test (keep-alive, answered with a parameters reply), `A4` break, `A8` disconnect.

## Data

Each packet starts with `op<<4 | seq`, where `seq` is a 4-bit counter that wraps and is **kept separately for each
direction**. The first packet of a message carries a 2-byte big-endian message length, then 5 data bytes; later
packets carry 7.

| Op | Meaning |
|---|---|
| `0` | waiting for an ACK; more packets follow (block size reached) |
| `1` | waiting for an ACK; this is the last packet |
| `2` | no ACK expected; more packets follow |
| `3` | no ACK expected; last packet |
| `9x` / `Bx` | ACK not ready / ready; `x` is the next sequence number expected |

Worked example (all of it is replayed byte for byte in `crates/opendiag-proto/tests/tp20.rs`):

```
740: 10 00 02 10 89     we send a 2-byte message  10 89  (op 1, seq 0)
300: B1                 module ACKs, expecting seq 1
300: 10 00 02 50 89     module replies  50 89  (its own seq 0)
740: B1                 we ACK
740: 11 00 02 21 01     our next message uses seq 1
```

## How the link behaves

`Tp20Link` waits the module's `T1` (at least 50 ms) for an ACK, leaves the module's `T3` between our packets, and sends
`block size` packets before waiting for an ACK. An ACK "not ready" extends the wait. A break, a disconnect, a wrong
sequence number or data arriving while we wait for an ACK is an error (it does not guess). The channel is closed with a
disconnect when the link is dropped.

Two readings go beyond the source and are **our assumptions**: the module's `T3` is the minimum gap we leave between
our packets, and its block size is how many packets we send before waiting.

## Not verified

A real module may differ, for example by sending its reply before acknowledging ours (which this client reports as an
error), or by using different timings. The only evidence is one published capture.
